## 已确认需求

依据需求说明及 D10～D14：

- 员工通过企微机器人提问，机器人先回答，需要时转人工，记录问题、反馈和评价。
- 任一条件成立时转人工：员工明确未解决、主动要求人工、机器人无法回答、问题需要人员实际操作。
- 所有问题均记录，包括机器人直接解决的问题；是否全部创建正式工单尚未确定。
- 人工处理结果由员工确认；未解决继续处理，确认解决后可以结单。
- 解决结果与满意度分开。人工评价自愿，未评价不阻止已确认解决的工单关闭；机器人回答不要求评价。
- 机器人回答后的解决确认、员工长期不回复、重开和低分处理细节仍待定。

用户本次表示预计负责后端，机器人不再归其负责。可以据此准备职责边界，不能宣称团队分工、技术路线和实施范围已经冻结。

## 后端设计要点

### 业务对象

以下是概念划分，不要求一一建表、拆服务或引入框架：

- 问题记录：来源、外部关联标识、可信提交人、必要内容、反馈、工单关联。多轮消息、一个会话多个问题及重复转人工如何归属需明确。
- 工单：编号、描述、分类、地点、优先级、提交人、处理组、负责人、状态和关键时间。建议地点与分类独立。
- 处理历史：操作人、动作、时间、必要的前后变化、原因、可见范围。不能只保存当前负责人和最终状态。
- 结果确认及评价：谁对哪轮处理结果作出什么确认；评价独立记录，未评价有明确含义。
- 通知任务：关联业务事件、对象、内容、发送结果、失败及重试关联，具体实现按规模选择。
- 基础配置：分类、地点、处理组、人员映射及角色权限。

字段、留存时长和附件访问方式需评审。“所有问题记录”不等于保存全部聊天或无限期保留。

### 状态与动作

候选主流程：`待分派 → 待接单 → 处理中 → 待员工确认 → 已关闭`。

- 待接单应有实际负责人；分派不等于接单，接单不自动等于首次人工响应。
- 处理人提交结果不代表员工确认解决。员工在待确认阶段明确未解决，继续处理并保留本轮历史。
- 草稿、等待补充、撤销、重复单、关闭后重开和改派目标状态另定，不自行补齐。
- 为每个动作明确执行人、允许状态、变更结果、时间记录和通知对象。接单／改派等并发操作应避免无提示覆盖他人变更。

### 对接契约

先明确业务语义，再决定接口路径、字段命名和技术栈。候选能力包括记录问题、追加反馈、转人工、查询、补充信息、员工确认、评价及通知回传。

| 事项 | 必须约定的语义 |
| --- | --- |
| 身份 | 外部来源的可信依据、调用方权限与员工权限；正文里的用户 ID 不能自行证明身份 |
| 原始标识 | 保留来源原始用户标识及其类型，映射结果与原值区分；未经核实不得混用加密标识、openid 和 userid；姓名工号读取能力单独验证 |
| 请求重试 | 来源请求编号在约定范围内唯一，同一业务请求重试返回原结果；编号复用但内容不同的处理另定，不引入内容哈希 |
| 关联 | 区分消息、会话、问题与工单编号，相同描述再次发送不自动等于重复报障 |
| 成功 | 持久化成功才能返回建单成功；通知失败与建单失败分别表达 |
| 查询 | 列表、详情、编号查询、附件及导出均执行权限限制 |
| 错误 | 区分信息不足、权限不足、状态不允许、资源不可访问、暂时故障；不向无权人员泄露详情 |
| 通知 | 明确谁重试、何时停止、如何回传及避免重复业务动作；发送成功不等于员工已读或确认 |

### 统计与时间

- 问题量与人工工单量分开，粒度与问题关联规则一致。
- 机器人已回复不等于自助解决，未反馈不等于已解决。
- 自动回执、接单、首次人工响应分别定义，FRT 起止动作待确认。
- 分别保留建单、分派、接单、首次人工响应、提交结果、员工确认和关闭时间；明确 ART 的终点，多轮处理不能静默覆盖历史。
- 满意度同时考虑有效评价数和评价覆盖情况，未评价不按零分或满意处理。
- 线上化率需要线下报障总量，没有分母不得伪造该指标。

## 获授权后的执行顺序与验证

本节只用于获相应授权后的任务规划，不启动自动开发。

1. 确定自建或接入既有系统、调用方、身份来源及前端／企微责任；不凭旧 Node／SQLite 原型冻结正式技术栈。
2. 优先收敛受理条件、状态与确认、分派兜底、权限。保留简短待决列表，不反复询问 D10～D14 已确认内容。
3. 交付必要的接口契约与数据设计，不先建设通用流程引擎、微服务或复杂消息平台。
4. 实现获批闭环：人工请求 → 建单 → 分派接单 → 处理结果 → 员工确认 → 关闭或继续处理 → 自愿评价；配套权限、历史与通知结果。
5. 再评审自动轮询、复杂 SLA、协作、合并和高级统计。分期不删除整体机器人问答主线。

实现后的针对性验收随批准范围确定：

| 场景 | 应验证结果 |
| --- | --- |
| 同一请求重试 | 不重复建单，原结果可恢复 |
| 越权访问或修改 | 列表、详情、动作和附件均遵循已定权限 |
| 无匹配处理人 | 工单进入约定兜底，可追踪，不虚报已接单 |
| 同时接单或接单与改派冲突 | 只允许合法变更，失败方得到可处理结果，历史一致 |
| 员工确认未解决 | 继续处理并保留历史，不依赖评分判断 |
| 员工确认解决但不评价 | 可以按已定规则结单 |
| 员工不回复或给低分 | 只执行获批规则，不默认解决或自动重开 |
| 内部备注与附件 | 不向无权人员展示或推送 |
| 建单成功但通知失败 | 工单保留，失败可追踪，重试不重复业务动作 |

这些是验收建议，不是已运行测试。按实际修改范围做最小充分验证；权限、事务和重要数据变更增加对应检查，仍须先满足全局执行限制。
