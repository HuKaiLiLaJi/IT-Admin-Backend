# IT／行政工单前端接口文档

新建工单的 `id` 与 `ticket_id` 使用 `ITYYYYMMDDNNNN`，例如 `IT202611110001`。日期按北京时间取建单日期，四位流水在同一数据库内跨处理组递增，每日从0001开始。已有UUID工单继续使用原编号，查询、动作及旧单关联均兼容。调用方应保存接口实际返回的完整字符串。单日达到9999后新建返回409，错误码 `ticket_number_exhausted`。同会话重试仍返回原单。

更新日期为2026-11-11。本文按当前本地代码整理，供前端开发和联调使用，覆盖登录、人员资料、工单、附件、分派处理、撤销、评价及统计。

员工补充接口及优先级选项已完成本地验证，GitHub和云端测试服务仍为此前版本。使用这些新增能力时，需要连接已加载本轮代码的服务。实际服务地址由后端提供，本文以同源相对路径表示接口地址。运行中服务的交互文档为 `/docs`，接口结构为 `/openapi.json`。

## 1. 请求约定

业务接口统一使用 `/api/v1` 前缀。下文均写完整路径。

| 参数位置 | 前端传递方式 | 示例 |
| --- | --- | --- |
| Header | 请求头 | `Authorization: Bearer <access_token>` |
| Path | 替换URL中花括号位置 | `/api/v1/tickets/{ticket_id}` |
| Query | URL查询字符串 | `/api/v1/tickets?scope=mine&limit=20` |
| JSON | JSON请求体 | `{"expected_version":2,"description":"追加说明"}` |
| FormData | 文件表单请求体 | 多个文件重复使用 `files` 字段 |

除了登录选项、测试账号列表、登录和健康检查，本文其余接口均需要员工登录取得的Bearer token。JSON请求设置 `Content-Type: application/json`。FormData请求由浏览器设置包含boundary的Content-Type。

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

工单操作身份由token关联的账号决定。员工工号通过登录和IAM映射关联到账号。现有建单、上传、查询及确认接口从登录身份取得提单人。JSON模型采用严格字段校验，额外提交 `submitter_employee_no`、`submitter_id` 或角色等未定义字段会返回422。

本文将响应对象定义为 `Ticket`、`File` 等便于说明的名称，实际JSON直接返回表中字段。JSON示例中的工单编号、会话和文件ID为占位示例，联调时使用接口实际返回的值。

## 2. 登录与人员资料

### 2.1 登录方式

`GET /api/v1/auth/login-options`

无需鉴权，无参数。成功200。

```json
{"employee_passwordless": true}
```

`employee_passwordless=true` 时，员工测试登录表单可以只提交工号。首次工号登录由后端查询IAM并建立账号，IAM配置及连接异常由后端返回。`false` 时员工表单使用工号和密码。

`GET /api/v1/auth/test-accounts`

无需鉴权，无参数。成功200，返回当前启用的预置测试账号。

```json
{
  "items": [
    {"username": "submitter", "display_name": "测试提交人"}
  ]
}
```

预置测试账号支持按 `username` 免密码登录。该能力与员工工号免密开关分别控制。

### 2.2 登录

`POST /api/v1/auth/login`

| JSON字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | string | 是 | 员工工号或预置测试账号，1～64字符，工号保留前导零 |
| password | string或null | 按登录方式 | 员工密码登录时填写，1～256字符。免密登录时省略 |

工号免密测试请求示例。

```json
{"username":"010591"}
```

密码登录请求示例。

```json
{"username":"010591","password":"<员工密码>"}
```

成功200。

```json
{
  "access_token": "<access_token>",
  "token_type": "bearer",
  "expires_in": 28800,
  "profile_warning": null
}
```

token有效期为8小时。`profile_warning` 为string或null，出现文字时展示人员资料刷新提示，登录仍已成功。

### 2.3 当前人员

`GET /api/v1/me`

需要Bearer，无参数。成功200。

```json
{
  "id": "<内部账号ID>",
  "username": "010591",
  "display_name": "员工姓名",
  "department": "部门名称",
  "email": null,
  "location": "Base地",
  "roles": ["submitter"],
  "group_scopes": {},
  "iam_profile": {
    "employee_number": "010591",
    "refreshed_at": 1794355200,
    "stale": false,
    "refresh_available": true
  }
}
```

`department`、`email`、`location` 可为null。`iam_profile` 在未关联IAM时为null。`group_scopes` 按角色列出处理组ID数组，例如 `{"dispatcher":["test-it"]}`。`stale` 表示资料缓存已达到一小时，`refresh_available` 表示服务配置了刷新能力。

| 角色 | 前端可对应的功能 |
| --- | --- |
| submitter | 本人提单、补充、确认、撤销和评价 |
| dispatcher | 授权处理组分派、改派和查看 |
| handler | 当前分配工单的接单、处理、结果及撤销审批 |
| manager | 授权处理组评价统计 |
| config_admin | 当前角色标识，配置维护接口后续落实 |

角色可叠加，动作权限还取决于工单归属、处理组和状态。前端根据角色展示入口，后端在每次请求中重新校验权限。

### 2.4 刷新本人资料

`POST /api/v1/me/profile/refresh`

需要Bearer，无请求体。成功200返回 `{"status":"ok"}`。成功后重新调用 `/api/v1/me` 更新显示。已有工单中的部门、邮箱及地点保存建单时快照。

### 2.5 退出

`POST /api/v1/auth/logout`

需要Bearer，无请求体。成功204且响应体为空。前端清理当前token、人员资料、会话、草稿及已上传文件ID。

## 3. 运维系统与处理人字典

以下接口均需要Bearer。

| 方法与路径 | 参数 | 权限 | 成功响应 |
| --- | --- | --- | --- |
| `GET /api/v1/service-systems` | 无 | 已登录 | 200，`{"items":[{"id":"test-office","name":"测试办公系统","group_id":"test-it"}]}` |
| `GET /api/v1/support-groups` | 无 | dispatcher | 200，授权组 `{"items":[{"id":"test-it","name":"测试IT组"}]}` |
| `GET /api/v1/support-groups/{group_id}` | Path `group_id`，string | 授权组dispatcher | 200，`{"id":"test-it","name":"测试IT组"}` |
| `GET /api/v1/support-groups/{group_id}/handlers` | Path `group_id`，string | 授权组dispatcher | 200，`{"items":[{"id":"test-handler","display_name":"处理人姓名"}]}` |

建单传运维系统的 `id`。分派及改派传处理人的内部 `id`。正式运维系统分类和处理组清单待确认，前端从接口获取当前有效选项。

## 4. 会话与创建工单

### 4.1 创建会话

`POST /api/v1/conversations`

需要Bearer及submitter角色。

| JSON字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| previous_ticket_id | string或null | 否 | 关联本人已关闭或已撤销的旧工单，1～128字符。普通建单省略 |

无关联旧单时提交 `{}`。请求体仍须提供。

成功201。

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "submitter_id": "<内部账号ID>",
  "previous_ticket_id": null,
  "created_at": 1794355200,
  "ticket_id": null
}
```

保存响应 `id` 作为后续建单的 `conversation_id`。同一会话最多对应一张工单。

### 4.2 恢复会话

`GET /api/v1/conversations/{conversation_id}`

Path `conversation_id` 为创建会话返回的string。需要该会话创建人的Bearer，无Query和请求体。成功200，字段同创建会话响应。已建单时 `ticket_id` 为工单编号，尚未建单时为null。

### 4.3 创建工单

`POST /api/v1/conversations/{conversation_id}/ticket`

Path `conversation_id` 为会话UUID。需要会话创建人的Bearer及submitter角色。

| JSON字段 | 类型 | 必填 | 约束及默认值 |
| --- | --- | --- | --- |
| service_system_id | string | 是 | 当前有效运维系统ID，去首尾空白后1～128字符 |
| title | string | 是 | 去首尾空白后1～200字符 |
| description | string | 是 | 去首尾空白后1～10000字符 |
| priority | string或null | 否 | `P1`、`P3` 或null，省略保存为空 |
| location | string或null | 否 | 去首尾空白后最多200字符，省略、null及空白沿用账号地点 |
| file_ids | string[] | 否 | 默认 `[]`，最多5项，每项去首尾空白后1～128字符 |

```json
{
  "service_system_id": "test-office",
  "title": "打印机无法连接",
  "description": "员工确认的故障说明",
  "priority": "P3",
  "file_ids": ["22222222-2222-4222-8222-222222222222"]
}
```

首次成功201，返回 `Ticket` 及 `files`。同会话重复建单成功200，返回首次创建的工单及当前附件。前端保存 `ticket_id` 用于后续操作。重试中传入的有效新标题、描述、优先级和附件保持首次建单语义，补充需求使用第7节接口。

提单人、部门、邮箱由当前账号带入。工程师在分派阶段指定。优先级仅支持选择、保存和返回，优先级判定及处理规则暂缓。旧工单和未选择优先级的新工单返回 `priority=null`。

文件必须已上传、归属于当前提单人，并且尚未绑定其他工单。重复文件ID会返回422。建单、附件绑定及初始历史同事务提交。

## 5. 附件上传与下载

### 5.1 上传

`POST /api/v1/attachments`

需要Bearer及submitter角色，请求体为 `multipart/form-data`。

| FormData字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| files | File，允许重复字段 | 是 | 每次1～5个非空文件，单文件最多10 MiB，请求体最多50 MiB加64 KiB协议开销 |

前端上传示例。

```javascript
const form = new FormData()
for (const file of selectedFiles) form.append("files", file)
const response = await fetch("/api/v1/attachments", {
  method: "POST",
  headers: { Authorization: `Bearer ${accessToken}` },
  body: form
})
const data = await response.json()
if (!response.ok) throw new Error(data.detail?.message || "上传失败")
const fileIds = data.items.map(file => file.file_id)
```

成功201。

```json
{
  "items": [
    {
      "file_id": "22222222-2222-4222-8222-222222222222",
      "file_name": "报错截图.png",
      "size": 204800,
      "content_type": "image/png",
      "created_at": 1794355200
    }
  ]
}
```

每项为 `File` 对象。`size` 单位为字节，`created_at` 为Unix秒整数。文件名经过路径及控制字符清理，长度1～255字符。`content_type` 保存上传声明的媒体类型。整批校验或保存失败时回滚整批。上传完成后保存 `file_id`，建单或补充时通过 `file_ids` 绑定。

### 5.2 下载

`GET /api/v1/attachments/{file_id}`

Path `file_id` 为上传返回的string。需要Bearer，无Query和请求体。未绑定文件由上传者下载，已绑定文件按当前工单查看权限校验。

成功200返回二进制，`Content-Type` 为 `application/octet-stream`，`Content-Disposition` 为attachment并携带UTF-8文件名。前端通过带鉴权头的fetch读取Blob，使用详情里的 `file_name` 作为下载名称。JSON错误响应需要按HTTP状态单独处理。

## 6. 工单列表与详情

### 6.1 查询列表

`GET /api/v1/tickets`

需要Bearer，无请求体。

| Query字段 | 类型 | 必填 | 默认值及约束 |
| --- | --- | --- | --- |
| scope | string | 否 | 默认 `visible`，可选 `visible`、`mine` |
| status | string | 否 | 单个第6.3节英文状态，省略查询全部当前可见状态 |
| q | string | 否 | 最多200字符，去首尾空白后匹配标题、初始描述、系统名称子串或完整工单编号 |
| service_system_id | string | 否 | 最多128字符，按运维系统ID过滤 |
| limit | integer | 否 | 默认20，范围1～100 |
| offset | integer | 否 | 默认0，最小0 |

```http
GET /api/v1/tickets?scope=mine&status=in_progress&q=打印机&limit=20&offset=0
Authorization: Bearer <access_token>
```

中文关键词由URLSearchParams等方式编码。多个筛选条件同时生效。排序采用更新时间无关的创建时间倒序，同一创建秒内按ID倒序。

成功200，`items` 中每项为 `Ticket`，`total` 为当前权限及筛选条件下的总数。

```json
{"items":[],"total":0,"limit":20,"offset":0}
```

`scope=mine` 要求submitter角色，严格查询本人提交的工单。员工“我的工单”使用该值，多角色员工也仅返回本人提交记录。`visible` 按本人提交、当前分配和授权分派处理组取权限并集。

查询待处理工单的状态集合、多状态查询及中文状态入参仍待定，当前按单个英文 `status` 调用。

### 6.2 获取详情

`GET /api/v1/tickets/{ticket_id}`

需要Bearer。Path `ticket_id` 为建单返回的工单编号，Query可选 `scope`，取值及默认值同列表，无请求体。

```http
GET /api/v1/tickets/IT202611110001?scope=mine
Authorization: Bearer <access_token>
```

成功200返回 `Ticket`，并追加第6.5节数组及评价字段。当前身份不可见或记录不存在统一404。

### 6.3 工单状态

| status | 展示名称 |
| --- | --- |
| pending_assignment | 待分派 |
| pending_acceptance | 待接单 |
| in_progress | 处理中 |
| awaiting_confirmation | 待员工确认 |
| closed | 已关闭 |
| cancelled | 已撤销 |

当前员工确认已解决后直接进入closed。接口表中提出的待补全、独立已解决状态及相关转换规则仍待确认。

### 6.4 Ticket公共字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id、ticket_id | string | 同一个工单编号，后续Path使用该值 |
| conversation_id | string | 建单会话UUID |
| submitter_id | string | 提单人内部账号ID |
| service_system_id | string | 运维系统ID |
| system | string或null | 当前运维系统名称 |
| group_id | string | 处理组ID |
| title、description | string | 初始标题及描述 |
| priority | string或null | P1、P3或null |
| department、email、location | string或null | 建单时人员资料及地点快照 |
| issue_id | string或null | 问题记录关联扩展字段 |
| status | string | 第6.3节状态 |
| assignee_id | string或null | 当前处理人内部账号ID |
| engineer_employee_no | string或null | 当前处理人已关联IAM的工号，保留前导零。未分派或无映射时为空 |
| version | integer | 当前工单版本，动作请求使用该值 |
| result_round | integer | 当前处理结果轮次，初始为0 |
| created_at、updated_at | integer | Unix秒时间戳 |
| created_at_iso、updated_at_iso | string | ISO8601字符串，时区为北京时间+08:00 |
| assigned_at、accepted_at | integer或null | 分派、接单时间，Unix秒 |
| result_submitted_at、confirmed_at | integer或null | 当前结果提交及员工确认时间，Unix秒 |
| closed_at、cancelled_at | integer或null | 关闭、撤销时间，Unix秒 |
| previous_ticket_id | string或null | 会话所关联的旧工单编号 |
| cancellation_requires_approval | integer | 0或1，表示当前撤销是否需要申请审批 |

建单和附件／补充动作响应另外带 `files`。列表及其他工单动作返回公共字段。前端在动作成功后重新读取详情，取得最新历史、结果和评价等信息。

### 6.5 详情追加字段

| 字段 | 类型 | 主要内容 |
| --- | --- | --- |
| files | File[] | 第5节附件元数据，旧单无附件时为 `[]` |
| history | object[] | 按id升序的流转记录，字段见下表 |
| results | object[] | 按round升序的处理结果 |
| cancellation_requests | object[] | 按sequence升序的撤销申请 |
| evaluation | object或null | 当前评价 |
| evaluation_history | object[] | 按id升序的评价修改记录 |
| evaluation_deadline_at | integer或null | 评价截止时间，Unix秒 |
| evaluation_locked | boolean | 当前评价是否锁定 |

| 数组或对象 | 字段及类型 |
| --- | --- |
| history[] | `id` integer，`ticket_id` string，`action` string，`actor_id` string，`from_status` string或null，`to_status` string，`created_at` integer，`from_assignee_id`／`to_assignee_id` string或null，`note` string或null，`result_round` integer或null，`cancellation_request_id` string或null |
| results[] | `ticket_id` string，`round` integer，`handler_id` string，`content` string，`submitted_at` integer，`confirmation` 为resolved／unresolved或null，`confirmed_by` string或null，`confirmed_at` integer或null |
| cancellation_requests[] | `sequence` integer，`id` string，`ticket_id` string，`requested_by` string，`reason` string，`requested_at` integer，`status` 为pending／approved／rejected／superseded，`decided_by`／`decision_reason` string或null，`decided_at` integer或null |
| evaluation | `ticket_id` string，`rating` 为good／neutral／bad，`reason` string或null，`source` 为active／automatic，`actor_id` string或null，`created_at`／`updated_at` integer |
| evaluation_history[] | `id` integer，`ticket_id` string，`rating` string，`reason` string或null，`source` string，`actor_id` string或null，`ticket_version` integer，`created_at` integer |

上述时间整数均为Unix秒。转JavaScript Date时乘以1000，界面统一按Asia/Shanghai展示。工单描述、补充文字及历史备注按纯文本渲染。

`history.action` 可返回 `created`、`assigned`、`reassigned`、`accepted`、`note_added`、`result_submitted`、`confirmed_resolved`、`confirmed_unresolved`、`cancelled`、`cancellation_requested`、`cancellation_approved`、`cancellation_rejected`、`attachments_added`、`supplement_added`。评价变更读取 `evaluation_history`。

## 7. 员工补充文字与附件

`POST /api/v1/tickets/{ticket_id}/supplements`

Path `ticket_id` 为原工单编号。需要当前提单人的Bearer及submitter角色。允许待分派、待接单、处理中和待员工确认四个阶段。

| JSON字段 | 类型 | 必填 | 约束及默认值 |
| --- | --- | --- | --- |
| expected_version | integer | 是 | 最新详情的version，最小1 |
| description | string或null | 条件必填 | 去首尾空白后最多10000字符，空白按无文字处理 |
| file_ids | string[] | 条件必填 | 默认 `[]`，最多5项，每项去首尾空白后1～128字符 |

文字和附件至少一项非空。

```http
POST /api/v1/tickets/IT202611110001/supplements
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "expected_version": 2,
  "description": "重新启动后仍然报错",
  "file_ids": []
}
```

成功200返回更新后的 `Ticket` 和 `files`。实际补充时version增加一次，状态保持当前值。文字以 `history.action=supplement_added` 保存，`note` 保存补充原文，`actor_id`、`created_at` 保存人员与时间，初始description保留。

文件绑定、版本和历史同事务提交。仅提交已绑定同单的附件且无文字时返回当前工单及版本。相同文字携带最新版本再次提交会新增一条补充记录，响应丢失后先查询历史及版本核对。

原附件追加接口也可调用。

`POST /api/v1/tickets/{ticket_id}/attachments`

Path、身份及允许状态与补充接口相同。JSON必填 `expected_version` integer≥1和 `file_ids` string[]，文件数组长度1～5，每项约束同上。

```json
{"expected_version":2,"file_ids":["22222222-2222-4222-8222-222222222222"]}
```

成功200返回 `Ticket` 和 `files`。新增绑定时增加version及 `attachments_added` 历史，同单已有附件重复绑定保持当前版本。两个接口均拒绝重复文件ID、他人上传文件及已绑定其他工单的文件。

## 8. 分派、处理与员工确认

本节所有接口需要Bearer，Path `ticket_id` 为工单编号，请求体为JSON。

### 8.1 分派和处理动作

以下JSON示例列出每个接口的完整必填字段，version和人员ID在调用时替换为实际值。成功均为200，返回更新后的 `Ticket`。

| 方法与路径 | JSON请求示例 | 身份与允许状态 | 成功后的状态 |
| --- | --- | --- | --- |
| `POST /api/v1/tickets/{ticket_id}/assignments` | `{"expected_version":1,"assignee_id":"test-handler"}` | 授权组dispatcher，pending_assignment | pending_acceptance |
| `POST /api/v1/tickets/{ticket_id}/reassignments` | `{"expected_version":2,"assignee_id":"test-handler_backup","reason":"交接处理"}` | 授权组dispatcher，pending_acceptance或in_progress | pending_acceptance |
| `POST /api/v1/tickets/{ticket_id}/accept` | `{"expected_version":2}` | 当前handler，pending_acceptance | in_progress |
| `POST /api/v1/tickets/{ticket_id}/notes` | `{"expected_version":3,"note":"已开始排查"}` | 当前handler，in_progress | in_progress |
| `POST /api/v1/tickets/{ticket_id}/results` | `{"expected_version":4,"result":"已恢复连接"}` | 当前handler，in_progress | awaiting_confirmation |

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| expected_version | integer | 最小1，使用最新详情version |
| assignee_id | string | 去首尾空白后1～128字符，使用第3节候选处理人id，须为当前处理组有效处理人 |
| reason、note、result | string | 去首尾空白后1～10000字符 |

改派目标须与当前处理人不同。改派后原处理人按当前权限重新计算可见性。处理备注对提单人公开。提交处理结果会增加 `result_round`。

### 8.2 员工确认结果

`POST /api/v1/tickets/{ticket_id}/confirmations`

需要当前提单人的Bearer及submitter角色，只能在awaiting_confirmation阶段调用。

| JSON字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| expected_version | integer | 是 | 最新version，最小1 |
| result_round | integer | 是 | 最新详情result_round，最小1 |
| outcome | string | 是 | `resolved` 或 `unresolved` |
| note | string或null | 否 | 去首尾空白后最多10000字符，空白按无备注处理 |

```json
{"expected_version":5,"result_round":1,"outcome":"resolved","note":"员工确认已恢复"}
```

成功200返回更新的 `Ticket`。resolved关闭为closed，unresolved返回in_progress。备注随确认动作保存至history。version或结果轮次过期时409，前端重新读取详情并让员工核对后提交。

## 9. 撤销及审批

本节均需要Bearer，Path `ticket_id` 为工单编号。成功均为200，返回更新后的 `Ticket`。

| 方法与路径 | JSON请求示例 | 条件 |
| --- | --- | --- |
| `POST /api/v1/tickets/{ticket_id}/cancel` | `{"expected_version":1,"reason":"已自行解决"}` | 当前提单人，待分派或待接单，且cancellation_requires_approval为0 |
| `POST /api/v1/tickets/{ticket_id}/cancellation-requests` | `{"expected_version":4,"reason":"申请撤销"}` | 当前提单人，待接单／处理中／待员工确认，且cancellation_requires_approval为1 |
| `POST /api/v1/tickets/{ticket_id}/cancellation-requests/{request_id}/decision` | `{"expected_version":5,"decision":"approved","reason":"确认无需继续处理"}` | 当前handler，待接单／处理中／待员工确认，目标申请为pending |

`expected_version` 为必填integer≥1。`reason` 为必填string，去首尾空白后1～10000字符。审批 `decision` 必填，可选approved或rejected。Path `request_id` 为详情 `cancellation_requests[].id`。

直接撤销及审批通过后进入cancelled。申请撤销和审批驳回保持当前主状态。工单曾进入处理阶段后，即使改派回待接单仍按申请审批流程处理。申请成功后重新读取详情取得申请ID。已有pending申请再次申请返回409。

## 10. 评价与统计

### 10.1 员工评价

`PUT /api/v1/tickets/{ticket_id}/evaluation`

需要当前提单人的Bearer及submitter角色，工单为closed且评价仍可修改。Path `ticket_id` 为工单编号。

| JSON字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| expected_version | integer | 是 | 最新version，最小1 |
| rating | string | 是 | good、neutral、bad |
| reason | string或null | 条件必填 | 中评、差评必填非空原因。去首尾空白后最多10000字符 |

```json
{"expected_version":6,"rating":"good","reason":"处理及时"}
```

成功200返回更新后的 `Ticket`。重新读取详情更新当前评价、评价历史及锁定状态。评价截止以详情 `evaluation_deadline_at` 为准，已到期或已有自动评价时返回409 `evaluation_locked`。

评价从关闭后即可提交，北京时间关闭次日起计算七个自然日，第七天结束时到期。例如11月6日关闭，11月14日零时到期。`active` 表示员工主动评价，`automatic` 表示到期自动好评。到期自动评价由后端命令执行。

### 10.2 评价统计

`GET /api/v1/evaluation-statistics`

需要manager角色Bearer，无请求体。Query可选 `group_id` string，去首尾空白后1～128字符。省略时汇总本人授权处理组，指定时须为本人授权组。

成功200。

```json
{
  "as_of": 1794355200,
  "group_ids": ["test-it"],
  "closed_total": 10,
  "active": {"good":4,"neutral":1,"bad":1},
  "automatic": {"good":2,"neutral":0,"bad":0},
  "active_total": 6,
  "automatic_total": 2,
  "unevaluated_total": 2,
  "overdue_unevaluated": 0,
  "participation_rate": 0.6
}
```

`participation_rate` 为主动评价数除以已关闭工单数，范围0～1，无已关闭工单时为null。`overdue_unevaluated` 表示已到期且尚未写入评价的工单数。`as_of` 为统计时点Unix秒。

## 11. 请求流程与失败恢复

1. 读取登录方式，登录取得token，再读取 `/api/v1/me` 和运维系统字典。
2. 创建会话并保存conversation_id。员工确认建单后，上传附件取得file_ids，调用同一会话的建单接口。
3. 建单成功保存ticket_id。员工列表和详情使用 `scope=mine`。
4. 提交补充、确认、撤销或评价前获取最新详情，使用其中version，确认时同时使用result_round。
5. 动作成功后刷新详情和列表。退出或切换账号时清理页面会话、草稿和文件ID。

建单请求超时后，先用原conversation_id恢复查询。已有ticket_id时读取原工单，尚未建单时可重试同一会话建单。会话创建响应丢失时，现有接口缺少按客户端请求号恢复会话的能力，前端应避免并发创建会话。

附件上传响应丢失后再次上传会生成新file_id。补充、附件追加及确认响应丢失后，先读取详情核对历史、附件、结果轮次及版本，再决定后续动作。旧version重试会返回409。

## 12. 错误响应

业务错误示例。

```json
{"detail":{"code":"version_conflict","message":"工单已更新，请重新读取后再操作"}}
```

请求结构或字段约束错误示例。

```json
{
  "detail": {
    "code": "invalid_request",
    "message": "请求字段无效",
    "fields": [
      {"loc":["body","title"],"type":"missing","msg":"Field required"}
    ]
  }
}
```

`detail.fields` 在请求模型校验错误时提供，业务校验错误可仅包含code和message。前端优先显示 `detail.message`，按需将fields映射至表单。

| HTTP状态 | 常见code | 前端处理 |
| --- | --- | --- |
| 401 | unauthenticated | 清理失效会话，重新登录 |
| 403 | forbidden | 提示权限不足，刷新当前身份及可操作入口 |
| 404 | not_found | 提示记录不存在或不可访问 |
| 409 | version_conflict、result_round_conflict、invalid_ticket_state | 刷新详情并核对当前状态和版本 |
| 409 | cancellation_approval_required、cancellation_pending、cancellation_decided | 根据最新详情展示撤销或审批进度 |
| 409 | evaluation_locked | 更新评价锁定显示 |
| 409 | iam_identity_conflict、iam_not_linked | 展示人员关联提示 |
| 413 | invalid_attachment | 提示文件数量、大小或上传格式限制 |
| 422 | invalid_request、invalid_service_system、invalid_attachment、empty_supplement、invalid_assignee、same_assignee、evaluation_reason_required | 根据提示修正字段或选择项 |
| 503 | storage_unavailable及IAM连接／配置相关code | 保留当前输入并提示稍后处理，写操作按第11节恢复核对 |

错误code还可能随具体IAM查询失败类型变化，前端对未知code保留按HTTP状态和message展示的处理。

## 13. 联调注意事项

当前服务提供同源页面和API。独立前端开发服务器可通过开发代理访问后端，生产同源路径由部署配置安排。后端当前配置以同源访问为基础。

`GET /health` 无需鉴权，无参数，成功200返回 `{"status":"ok"}`，用于服务可用性检查。

正式机器人服务凭证、可信员工身份传递、正式分类、待处理状态集合及待补全流转继续待双方确定。前端对接当前已实现字段和动作，优先级当前按可选P1/P3保存及展示。

原接口表用于双方需求核对。本文的参数和行为依据当前代码，进一步调用及重试说明见 [工单接口调用说明](工单接口调用说明.md)，发布及验收进度见 [快速恢复](quick-resume.md)。
